# ② 计划

**目的**：把决策卡变成一份能直接开工、每一步都能被验证的计划。
**进入条件**：闸门 A 有效；或用户跳过①直接要计划（先提炼最小决策卡，经 `gate A` 确认）；或执行中触发一级升级。
**产出**：`.decision/plan.json`，通过闸门 B。

## 目录
- 清单与步骤
- plan.json 字段
- 闸门 B
- 一级升级回到这里时
- 规模适配与常见坑

## 清单

```
② 计划
- [ ] 1 读决策卡：目标、编号的成功标准、A1、止损条件
- [ ] 2 从成功标准倒推里程碑
- [ ] 3 拆成可验证的小步，写 covers 对应成功标准
- [ ] 4 排序：验证 A1 的步骤放最前；写 depends_on
- [ ] 5 每步写完成判据、验证方法，能写命令的写 verify_cmd
- [ ] 6 标出不可逆步骤
- [ ] 7 写 if-then 预案
- [ ] 8 快速事前验尸 → 早期信号
- [ ] 9 指定第一步，check plan → gate B
```

**1 读卡**：成功标准必须是编号条目，计划用编号建立覆盖关系。

**2 倒推里程碑**：到达成功标准之前必须成立的 2-5 个**状态**（"1 家店试运行 2 周无故障"），不是一段工作（"开发"）。

**3 拆步**：合格的一步一个工作时段内能做完（`estimate_h` 超过 8 会被提示），有可观察的完成判据，做坏了能回滚。每步的 `covers` 写它推进哪几条成功标准；每条成功标准至少被一个步骤覆盖（高风险档强制）。

**4 排序**：先做验证 A1 的最小实验（`tests_assumption: "A1"`），再做确定性高的工作。有先后关系的写 `depends_on`，脚本会阻止提前开始。

**5 验证**：根据 [verification-strategy.md](verification-strategy.md) 的交付类型选择验证手段。运行命令前先查看 `de.py preflight` 的只读报告。`verify_cmd` 按 Shell 运行，不是沙箱；即便只写 `test`/`pytest` 也可能有副作用。高风险命令需宿主审批和隔离执行，不得因 Gate B token 存在便假定授权安全。`done_when` 写完成时世界的样子；`verify` 写怎么证明。**能用命令证明的，一定写 `verify_cmd`**（测试、构建、lint、`curl -f` 检查、`test -f 文件`），这是可由脚本检查退出状态的一类证据，但不能证明命令完全无副作用或验收充分。不能写命令的（访谈、用户确认、截图），完成时用 `--artifact` 指向证据文件。

**6 不可逆步骤**：删数据、迁移、发布到生产、改权限、对外发送……标 `"irreversible": true`。开始这一步时脚本会要求两步确认；高风险档还要配宿主审批（见 permissions.md）。

**7 if-then 预案**：为最可能的 2-3 个障碍各写一句"如果 X，就 Y"，Y 是具体动作。

**8 事前验尸**：假设三周后失败了，最可能的 3 个原因各配一个预防动作（加进步骤）或早期信号（写进 `early_signals`）。只做一轮。

**9 第一步**：今天就能开始、当天能看到结果。

## plan.json 字段

| 字段 | 类型 | 说明 | 改了会让闸门 B 失效 |
|---|---|---|---|
| `risk` | `standard` / `high` | 由 init 设定 | 是 |
| `steps[].id` | 整数或字符串 | 唯一 | 是 |
| `title` / `done_when` / `verify` | 字符串 | 必填 | 是 |
| `verify_cmd` | 字符串 | 在项目根目录用 shell 执行；退出码 0 为通过 | 是 |
| `depends_on` | 数组 | 前置步骤 id | 是 |
| `covers` | 数组 | 成功标准编号 | 是 |
| `tests_assumption` | 字符串 | 如 `A1` | 是 |
| `irreversible` | 布尔 | 不可逆步骤 | 是 |
| `estimate_h` | 数字 | 预计小时 | 是 |
| `status` / `fails` / `spent_h` / `evidence` 等 | — | 由脚本维护，不要手改 | 否 |
| `if_then` / `first_step` | — | 执行预案与第一步（属于批准过的计划） | **是**
| `early_signals` / `milestones` | — | 辅助说明，不绑定批准 | 否 |

`verify_cmd` 会被脚本执行，所以闸门 B 的 preview 会把每条命令列出来请用户确认；之后任何人改了命令，闸门 B 都会失效。

## 闸门 B

1. `python3 scripts/de.py check plan`：`errors` 清零；`warnings` 逐条向用户说明或修正。
2. `python3 scripts/de.py show` 把计划表给用户看。
3. `python3 scripts/de.py gate B` 得到 token 和 preview，**展示给用户，等用户回复同意**，再带 `--confirm` 重跑。

**人工闸门清单**（无代码执行时）：每步有判据和验证方法；没有超过一个工作时段的步骤；每条成功标准被覆盖；验证 A1 的步骤在前两步；不可逆步骤已标出；至少 2 条具体的 if-then；第一步今天能开始。

## 一级升级回到这里时

步骤处于 `needs_replan`。只处理这一步：拆小、换做法、补前置步骤（新增步骤并写进 `depends_on`）。改完运行 `replan ID --note "改了什么、为什么"`，脚本会核对这一步确实改过；然后重新 `gate B`。确有理由不改（例如外部服务临时故障），用 `replan ID --note … --waive 理由`，同样需要用户确认，且再失败一次会立即再次升级。

## 规模适配与常见坑

- 一天内的小任务：计划可只有 3 步，省略里程碑和事前验尸；判据与验证不能省。
- 第一步是"搭建项目框架"这类无法证伪方向的准备工作。
- 验证方法写成"自测通过"——谁测、测什么、看到什么算通过？
- 能写 `verify_cmd` 却只写了文字验证方法。
- 计划里悄悄混进了决策卡"非目标"里的东西。

完整示例见 [worked-example.md](worked-example.md)。


## R2｜验证证据覆盖（只读）

在执行前使用 `de.py preflight` 核对当前分支、用户未提交改动与验证命令；步骤完成后用 `de.py coverage` 将每条编号成功标准与 `covers`、步骤状态和证据质量逐条映射。

- `READY_FOR_INDEPENDENT_REVIEW` 只表示关联步骤的命令已通过/文件未改变；**不意味着该成功标准已真实满足**。
- 对真实 GUI、硬件、安全和外部 API 应明确验收工具、人工观察以及 `NOT_VERIFIED` 项。
- 若 `covers` 没有指向真实需求，脚本不能自动识别，这一部分由独立审查者负责。
