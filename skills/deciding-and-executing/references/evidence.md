# 设计依据

每条设计对应的来源。向用户解释"为什么这样做"时引用；不需要在每次执行中复述。

| 设计 | 依据 | 证据强度 |
|---|---|---|
| 不信任同一对话里的自我反驳，偏好外部证据 | Huang et al., ICLR 2024：无外部反馈的内在自我修正多数情况下不提升表现，有时下降 | 强（LLM 专项） |
| 推理过程不等于真实依据，结论要用证据核对 | Turpin et al., NeurIPS 2023：思维链解释会系统性地掩盖真实影响因素 | 强（LLM 专项） |
| 显式要求不迎合、置信度要说依据 | Sharma et al., ICLR 2024：基于人类偏好训练的助手普遍存在迎合倾向 | 强（LLM 专项） |
| 高风险时找独立信源，而非同一模型分饰多角 | Du et al., ICML 2024 多模型辩论有效；同质化辩论的回音室现象；Khan et al. 2024：辩论价值来自信息不对称 | 中（条件依赖） |
| 先计划再执行，计划拆成子任务 | Wang et al., ACL 2023 Plan-and-Solve：先拆子任务再执行，减少漏步错误 | 中（推理任务，非项目管理） |
| 一次只做一步、外置进度文件、无证据不宣布完成 | Anthropic Engineering 2025《Effective harnesses for long-running agents》：观察到代理倾向一次做太多、过早宣布完成；用功能清单 + 进度文件 + 端到端测试缓解 | 中（工程实践报告） |
| 先探索、再计划、再实现，并给出验证手段 | Claude Code 官方最佳实践：区分探索与执行，给模型验证自己工作的方法 | 中（工程实践） |
| if-then 预案 | Gollwitzer & Sheeran 2006 元分析（94 项检验，d≈0.65）；Sheeran 等 2024 更新（642 项检验，d 0.27–0.66） | 强（人类行为研究） |
| 止损条件写成"状态 + 期限"，事前写下 | Annie Duke《Quit》的 kill criteria 方法 | 弱-中（实践者方法论） |
| 事前验尸 | Gary Klein 的 pre-mortem 方法 | 中（决策科学传统） |
| 复盘区分决策质量与结果质量 | Annie Duke《Thinking in Bets》中"resulting"偏误 | 弱-中（实践者方法论） |
| 投入与可逆性成正比 | "单向门/双向门"决策框架 | 弱（经验法则） |
| 闸门交给脚本检查，而不是靠"请务必" | Anthropic 与 agentskills.io 的技能编写指南：关键检查用确定性代码，采用"计划—校验—执行"模式 | 中（工程实践） |
| 结案归档：过程工作区变成决策记录后删除 | 架构决策记录（ADR）的通行做法：决策理由长期保留，且与描述现状的文档分开；Anthropic 长任务代理实践：进度文件是给下一个会话读的，结束后不应继续当作现状 | 弱-中（工程惯例） |
| 脚本只宣称能验证的东西；授权分脚本、流程、宿主三层 | 外部评审指出"授权不应是模型自填字段"；Claude Code 权限文档：ask 规则在自动模式下也会弹出审批，但只匹配命令文本、不是安全边界；Codex rules 的 prompt 决策 | 中（官方文档 + 设计判断） |
| 命令证据绑定代码指纹，代码一变证据过期 | 外部评审"仅有旧版本测试证据不得视为新版本验证成功"；与 CI 只认当前提交结果的惯例一致 | 中（工程惯例） |
| 失败达到上限后脚本阻止继续，要求改计划或记录豁免 | 外部评审 P1-03：升级若只是建议，就会被忽略 | 中（设计判断，有回归测试） |
| 一级/二级升级分开 | 设计选择：步骤级失败多数是做法问题，不必动方向；只有假设被证伪才回到方向层，避免"一出错就推倒重来" | 弱（设计判断，待使用数据验证） |

## 已知局限

- 这套流程整体没有经过对照实验验证；单项依据的强度不等于组合后的效果。
- if-then 预案的证据来自人类行为研究，用在"给 AI 写预案"上是类比迁移，不是直接证据。
- 最大的使用风险是把"走完流程"当成"想清楚了"。流程只保证没漏步骤，不保证每一步做得深。
- 两步确认的 token 不能证明确认者是人；Agent 若违反流程自己取 token 自己确认，脚本无法发现。真正的人工授权依赖宿主审批规则（permissions.md）。
- 文件证据只证明"这个文件存在且内容是这样"，不证明文件内容真实；文字证据完全不可验证，所以单独标出。
