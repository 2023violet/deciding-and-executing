# ④ 审查与复盘

两件事，时机不同：**审查**在交付前，看"东西"有没有问题；**复盘**在阶段结束后，看"做法"下次怎么改。止损触发而停下的项目，跳过审查，直接复盘。

## A. 交付前审查

**进入条件**：通过闸门 C，或用户说"可以上线了吧"。

1. **对照成功标准**：按 [verification-strategy.md](verification-strategy.md) 选择和检查实际证据，再运行 `de.py coverage` 取出逐项证据清单，检查命令/文件是否仍有效，再独立确认测试是否真的覆盖用户所需的行为；逐条列出证据。缺证据的条目标出来，不算通过——即使"看起来没问题"。
2. **对照非目标**：有没有做了决策卡里说不做的东西？有没有临时方案冒充正式方案？
3. **找问题**：以"上线前必须找出问题"为目标——最可能出错在哪？哪条假设到现在还没被验证？用户第一次使用最可能卡在哪？
4. **独立审查（高风险时）**：同一对话里审自己的产物，独立性有限。建议用户开一个新会话或换一个模型，只给产物和成功标准，不给开发过程和你的推理。
5. **回归验证**：`python3 scripts/de.py verify --all`，让所有命令证据对应当前代码。
6. **结论**（三选一，用脚本记录）：
   - 可交付 → `review --verdict pass`（有未完成步骤、过期命令证据、高风险档的纯文字证据、或带阻断项时，脚本拒绝）
   - 修复后可交付 → `review --verdict fix --blocker "必修项" ...`，每个必修项作为新步骤加回计划（会要求重新确认 gate B）
   - 不可交付 → `review --verdict fail --blocker "原因"`，判断是一级还是二级升级

   脚本返回 preview 和 token：**展示给用户，等用户同意**，再带 `--confirm` 重跑。审查结论绑定当时的代码指纹和计划；之后代码或计划变化，结论自动失效，需要重新审查。

## B. 复盘

`.decision/retro.md` 已由 init 创建。归档时脚本会检查「原本预期」「实际发生」「差异的原因」三节都有实质内容，模板占位不算。按顺序回答四个问题，答案以文件为准（决策卡、plan.json、events.jsonl），不凭回忆：

1. **原本预期什么**：读决策卡和计划。
2. **实际发生什么**：读 `progress.md`。
3. **差异的原因**：区分"决策质量"和"结果质量"——好决策可能碰上坏运气，坏决策也可能走运。只看结果评价决策，会学到错误的教训。问：以当时掌握的信息，这个决定合理吗？当时有没有便宜的方法拿到更多信息？
4. **下次保持什么、改变什么**：每条落成一个具体动作或一条规则。

## C. 回写

- 决策卡的关键假设表：每条标上 已证实 / 已证伪 / 未验证，并写依据。
- 估算偏差：对比各步 `estimate_h` 与 `spent_h`，若系统性偏差（例如总是低估一倍），告诉用户下次计划时乘上这个系数。
- 可迁移的经验：在 retro.md 的"教训去向"表里逐条决定去处——规则文件（下一个 Agent 不知道就会做错）、docs、本技能的 Gotchas，或不记录。没有新教训是合法结果。
- 止损触发而停下的项目也要复盘：停得是否及时？信号是否本可以更早出现？

审查结论为 pass（或决定止损、放弃）且复盘写完，即通过闸门 D，进入 [stage-5-closeout.md](stage-5-closeout.md)。

## 本阶段常见坑

- 用户问"可以上线了吧"时顺着说"可以"。
- 复盘只写"下次注意"，没有落成具体动作。
- 把失败全部归因于运气，或全部归因于决策。


**R2 验证边界**：`coverage` 的“可供独立审查”并非“已验证完成”。对于需要真实设备、浏览器画面或用户验收的项目，缺少相应观察时，即使命令全部退出码为 0，也必须写明 `NOT_VERIFIED`。
