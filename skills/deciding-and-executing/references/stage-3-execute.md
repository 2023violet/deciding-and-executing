# ③ 执行

**目的**：一次只推进一步，每一步都有证据；遇到问题按类型就地处理，不在执行中重新辩论方向。
**进入条件**：闸门 B 有效（计划或决策卡改动后会失效，脚本会拒绝执行类命令）。
**产出**：更新后的 `plan.json` 与 `progress.md`；全部步骤 done 时通过闸门 C。

## 单步循环

每一步走五个动作：

1. **对齐**：运行 `python3 scripts/de.py status`，说出当前步骤、完成判据，并检查 `escalations` 和计划里的早期信号。新会话开始时必做——不要凭记忆猜上次做到哪。
2. **开工前确认基础是好的**：上一步留下的东西还能用吗？在坏掉的基础上做新东西，只会让问题更难查。
3. **只做这一步**：`step ID --status in_progress`（依赖未完成会被拒绝；不可逆步骤会要求两步确认，preview 必须给用户看）。发现别的问题，记到 `progress.md` 的"待办/观察"，不顺手展开。
4. **验证**：
   - 有 `verify_cmd` → 直接 `step ID --status done`，脚本当场执行命令，通过才标记完成。
   - 没有命令 → `step ID --status done --artifact 证据文件`；标准档也可以 `--evidence "文字"`，但会被记为未验证。
   - 做完但还没法验证 → `step ID --status implemented`。
   - 验证失败 → `fail ID --note "现象" [--hours 已用小时]`，再按下方分诊表处理。
   - 投入时间用 `--hours` 记下，超过预计一倍时 `status` 会提示一级升级。
5. **检查升级条件**：`fail` 返回 `escalate: true` 时，步骤已自动变为 `needs_replan`，脚本会拒绝继续执行它——回到 stage-2-plan.md 的"一级升级回到这里时"。`status` 列出其他 `escalations` 时同样停下处理。

## 问题分诊

执行中冒出的问题先归类。拿不准就选最接近的一类，不在分类上花时间。

| 类型 | 信号 | 做法 |
|---|---|---|
| **诊断** | 报错、结果不对、行不通 | 列 3 个互相独立的可能原因，按排除成本从低到高逐个验证，每次只改一个变量。不直接跳到"最可能"的那个——第一直觉锁死是最常见的浪费。 |
| **选择** | 实现路径分叉 | 先问：以后改起来贵不贵？便宜 → 直接给推荐和一句理由，继续。贵 → 设计一个最小实验比较，或作为二级升级回到①。 |
| **卡壳** | 不知道该查什么、用什么工具 | 说清已试过什么，列出这类问题通常涉及的关键词、工具、隐含前提，挑最便宜的先试。 |
| **漂移** | 越做越大，或做的东西与目标对不上 | 把当前在做的事和决策卡的目标、非目标逐条比对：有意调整 → 修订决策卡并记录；无意漂移 → 回到计划。 |
| **启动** | 不知从何下手、一直拖着 | 把当前步骤继续拆，直到出现一个 15 分钟内能开始的具体动作，只做那一个。 |

## 求助时的问题报告格式

向这个对话、另一个模型或人求助前，先整理成下面的格式。很多时候整理到第 4 项，答案已经出来了：

```
1. 目标：这一步要达到什么（贴完成判据）
2. 期望：我以为会发生什么
3. 实际：实际发生了什么（贴原始报错/数据，不要转述）
4. 已试：试过什么、各自的结果
5. 约束：不能改什么、时间预算
6. 猜测（可选）：我认为原因是……，依据是……
```

## 已完成的步骤需要重做

`reopen ID --reason "为什么"`：旧证据移入 `evidence_history`，步骤回到待做，已有的审查结论作废。不要手改 `plan.json` 的状态。

## 闸门 C

`status` 显示 `stage: review`：全部步骤 done，且没有 `unverified_steps`。注意 `stale_evidence_steps`（命令证据不对应当前代码）和 `note_only_done_steps`（只有文字证据）——它们不阻止进入④，但审查时要处理：前者运行 `verify --all`，后者向用户说明这些步骤没有可复核的证据。

**人工闸门清单**：
- [ ] 每一步都有对应的证据记录
- [ ] 没有处于"已实现未验证"的步骤
- [ ] "待办/观察"里的事项都已处理或明确延后

## 本阶段常见坑

- 修复失败后继续盲试第三、第四次——这正是一级升级要拦住的。
- 为了让验证通过而改 `verify_cmd`、放宽判据或删测试——闸门 B 会因此失效，必须向用户说明理由并重新确认。
- 手动编辑 `plan.json` 里的状态或证据来绕过脚本。
- 把多个步骤合并成一次大改动；出问题时将无法定位。
- 用户一句"感觉方向不对"就重开①。先问：是哪条假设被什么证据动摇了？
