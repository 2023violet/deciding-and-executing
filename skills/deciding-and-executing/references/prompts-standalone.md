# 六段独立提示词

用于没装这个 Skill 的环境（其他 AI、新会话）。它们是 SKILL.md 各阶段的压缩版，缺少脚本闸门，所以每段都把关键闸门写成了明确要求。按阶段选一段，复制后把方括号里的内容替换掉。

## 目录
- P1 定方向
- P2 交接：方向 → 计划
- P3 执行：单步推进
- P4 执行：遇到问题
- P5 审查与复盘
- P6 收尾与知识同步

---

## P1 定方向

```
先判断这个问题值不值得深想：如果低风险、可逆、需求明确，直接说"不用走流程"并回答。
否则按以下步骤，不要为了让我满意而弱化反对意见：
1. 重述我真正想解决的问题；如果我问错了问题，直接指出。
2. 列出我没说但默认成立的假设，标出哪些一旦不成立结论就要推翻。
3. 指出我可能不知道自己不知道的地方；涉及工具或路径选择时替我判断。
4. 给 2-4 个真正不同的方向，每个写最强论证（事实与推测分开）、最优条件、代价与风险。
5. 指出"只改变一个假设就能翻转结论"的那个假设。
6. 你能查到的自己查；只有我知道且会改变结论的，问我一个问题，附你的推荐答案，然后停下等我回答，不要替我回答。
我回答后给出：做/改/放弃、最大风险、最缺的证据、今天的最小一步、置信度及依据，
最后整理成一张决策卡：目标 / 成功标准（可验证）/ 非目标 / 关键假设 / 止损条件（状态+期限）。
我的问题是：[问题]
```

## P2 交接：方向 → 计划

```
这是我已经定下的决策卡：
[贴决策卡]
请把它变成执行计划，不要重新讨论方向：
1. 先检查决策卡：成功标准能否被验证？非目标和止损条件写了吗？缺的先补，标为"假设"让我确认。
2. 从成功标准倒推 2-5 个里程碑（每个是一个可检查的状态）。
3. 拆成小步：每步一个工作时段能完成、有可观察的完成判据、做坏了能回滚。
4. 排序：最先验证"最可能推翻整个方向的假设"，通常用一个低成本实验。
5. 每步写清验证方法——怎么证明它完成了。写不出来就继续拆。
6. 为最可能的 2-3 个障碍写"如果出现 X，就做 Y"，Y 要是具体动作。
7. 假设三周后失败，列最可能的 3 个原因，各配一个预防动作或早期信号。
8. 给出今天就能开始、当天能看到结果的第一步。
用表格输出：步骤 / 完成判据 / 验证方法 / 预计耗时 / 状态。
```

## P3 执行：单步推进

```
计划表和进度如下：
[贴计划表 + 进度日志]
现在只做下一步：
1. 先说出当前步骤和它的完成判据。
2. 只做这一步；发现的其他问题记下来，不顺手展开。
3. 完成后按判据给出证据：能用命令验证的，实际运行命令并贴出命令和退出码；不能的，给出证据文件的位置。
   只有文字描述的，标"已实现，未验证"，不要说"完成"。代码改动之后，之前的验证结果作废，需要重跑。
4. 更新进度日志：做了什么、证据、与计划的偏差、下一步。
5. 检查升级条件，触发就停下告诉我，不要继续：
   一级（回到计划，只改这一步）：同一步修两次仍失败 / 耗时超过预计一倍 / 步骤拆错了；
   二级（回到定方向，只重审被击中的假设）：止损条件触发 / 关键假设被证伪 / 外部约束变化 / 出现明显更优方案。
6. 回复结尾说清：当前步骤状态、证据、下一步。
```

## P4 执行：遇到问题

```
我在执行计划时遇到问题，先帮我判断它属于哪一类，再用对应做法，不要重新讨论整体方向：
- 诊断（报错、结果不对）：列 3 个互相独立的可能原因，按排除成本从低到高逐个验证，每次只改一个变量。
- 选择（路径分叉）：先判断以后改起来贵不贵；便宜就直接推荐，贵就设计一个最小实验比较。
- 卡壳（不知道查什么）：列出这类问题通常涉及的关键词、工具、隐含前提，挑最便宜的先试。
- 漂移（越做越偏）：把我现在做的事和决策卡的目标、非目标逐条比对，判断是有意调整还是无意漂移。
- 启动（不知从何下手）：把当前步骤拆到一个 15 分钟内能开始的动作。

决策卡：[贴]
当前步骤及完成判据：[贴]
期望：[ ]   实际：[贴原始报错/数据]
已试过：[ ]   约束：[ ]
```

## P5 审查与复盘

```
【交付前审查】以上线前必须找出问题为目标，不要安慰我：
1. 逐条对照成功标准给证据，缺证据的不算通过。
2. 对照非目标：有没有做了不该做的、有没有临时方案冒充正式方案？
3. 最可能出错在哪？哪条假设还没被验证？用户第一次用最可能卡在哪？
4. 结论：可交付 / 修复后可交付（列必修项）/ 不可交付。
成功标准：[贴]   产物：[贴或描述]

【复盘】
1. 原本预期什么（以决策卡和计划为准）  2. 实际发生什么（以进度日志为准）
3. 差异原因——分开"决策质量"和"结果质量"，不要只用结果评价决策
4. 下次保持什么、改变什么，每条落成一个具体动作
5. 把决策卡中每条关键假设标为 已证实 / 已证伪 / 未验证
```

提示：P5 的审查部分在新会话或另一个模型里做效果更好——只给产物和成功标准，不给过程。

## P6 收尾与知识同步

```
这段工作告一段落，请帮我收尾，让文档和规则文件重新等于代码现状。不要写新功能，不要删除任何文件。
1. 先用 git 看本次改了什么（git status、git diff --stat），列出改过的名字、命令、路径、功能。
2. 对每一项，搜索 README、docs/、AGENTS.md、CLAUDE.md 里所有提到它的地方，列出过时的位置。
3. 检查规则文件：CLAUDE.md 和 AGENTS.md 同时存在时，CLAUDE.md 是否导入了 AGENTS.md；
   规则里引用的路径和命令是否真实存在。
4. 修改时先删后加：删掉过时说法、已完成的待办、重复段落；就地改写，不追加"更新："段落；
   每个事实只留一个权威位置，其余改成链接。
5. 计划草稿、调试脚本、旧副本、已结束项目的过程文件，只列成删除候选并写理由，等我确认。
6. 用表格报告：每个知识面（文档、规则文件、决策记录、工作区残留）的状态，改了什么及依据，
   需要我决定的事项，遗留问题。
本次改过的名字（旧 → 新）：[ ]
```
