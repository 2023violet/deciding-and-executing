# 计划与执行

把决策卡变成每一步都能被验证的计划，然后一次只推进一步。

## 目录
- 写计划
- plan.json 字段
- 确认计划
- 执行一步
- 出了问题
- 失败到上限、回到计划时

## 写计划

```
- [ ] 1 从编号的成功标准倒推 2-5 个里程碑（状态，不是工作）
- [ ] 2 拆成小步：一个工作时段能做完、有可观察的完成判据、做坏了能回滚
- [ ] 3 每步写 covers（推进哪几条成功标准）；每条标准至少被一步覆盖
- [ ] 4 验证 A1 的最小实验放最前（tests_assumption: "A1"）；有先后的写 depends_on
- [ ] 5 每步写怎么算完成、怎么验证；能用命令证明的一定写验证命令
- [ ] 6 标出不可逆步骤（irreversible: true）
- [ ] 7 写 2-3 条"如果 X，就 Y"的预案（if_then）
- [ ] 8 事前验尸一轮：假设三周后失败，最可能的 3 个原因各配一个预防步骤或早期信号
- [ ] 9 指定今天就能开始的第一步（first_step）
```

一天内的小任务可以只有 3 步，省略里程碑和事前验尸；完成判据和验证不能省。

**验证命令**：
- 优先写 `verify_argv`（参数数组，不经 shell，各系统行为一致），例如 `["python", "-m", "pytest", "tests/test_order.py"]`。不知道写什么时，`check plan` 的 `suggested_verify_argv` 会列出仓库里已有的测试和检查入口（package.json 脚本、pytest、Makefile、just、cargo、go），合适就照抄。
- 需要管道、重定向时才写 `verify_cmd`，它交给系统 shell（Windows 上是 cmd.exe，`test -f`、`> /dev/null` 跑不通；`check plan` 会对这类写法给警告）。
- 验证命令不要往项目里写未被 Git 忽略的文件：执行期间代码一变，这次结果就不算数。
- 不能写命令的（访谈、截图、用户确认），完成时用 `--artifact` 指向证据文件。真实 GUI、硬件、外部 API 写明观察方式，做不到的标 `NOT_VERIFIED`。
- 怎么为不同交付类型选验证手段，见 [verification-strategy.md](verification-strategy.md)。
- 验证命令不是沙箱。运行前先看 `de.py preflight` 的只读报告；高风险命令需要宿主审批和隔离环境。

## plan.json 字段

| 字段 | 类型 | 说明 | 改了要重新确认计划 |
|---|---|---|---|
| `risk` | `standard` / `high` | 由 init 设定 | 是 |
| `steps[].id` | 整数或字符串 | 唯一 | 是 |
| `title` / `done_when` / `verify` | 字符串 | 必填 | 是 |
| `verify_argv` | 字符串数组 | 推荐。在项目根目录直接执行；退出码 0 为通过 | 是 |
| `verify_cmd` | 字符串 | 交给系统 shell；与 `verify_argv` 二选一 | 是 |
| `depends_on` | 数组 | 前置步骤 id | 是 |
| `covers` | 数组 | 成功标准编号 | 是 |
| `tests_assumption` | 字符串 | 如 `A1` | 是 |
| `irreversible` | 布尔 | 不可逆步骤 | 是 |
| `estimate_h` | 数字 | 预计小时 | 是 |
| `if_then` / `first_step` | — | 执行预案与第一步（属于批准过的计划） | **是** |
| `name` | 字符串 | 计划名称 | 是 |
| `early_signals` / `milestones` | — | 辅助说明 | 否 |
| `status` / `fails` / `evidence` 等 | — | 不写在 plan.json：它们在 `state.json`，只由脚本写入 | 否 |

## 确认计划

照 `next` 走：`check plan` 没有 error 后，`gate B` 的预览会列出每条将被执行的验证命令。**把预览给用户看，用户同意后**才带 `--confirm` 重跑。标准档在决策卡和计划一起写好时可以用 `gate AB` 一次确认；高风险档必须分开确认。之后改了命令或步骤结构，需要重新确认。

**没有脚本可用时**的人工检查：每步有判据和验证方法；没有超过一个工作时段的步骤；每条成功标准被覆盖；验证 A1 的步骤在前两步；不可逆步骤已标出；至少 2 条具体的预案；第一步今天能开始。

## 执行一步

1. **对齐**：新会话先运行 `de.py status`（或看会话钩子注入的简要状态），按 `next` 继续，不凭记忆猜上次做到哪。
2. **确认基础是好的**：上一步留下的东西还能用吗？
3. **只做这一步**：`step ID --status in_progress`。不可逆步骤会先要求用户确认。发现别的问题，记到 `progress.md` 的"待办/观察"，不顺手展开。
4. **验证**：
   - 有验证命令 → `step ID --status done`，脚本当场执行，通过才算完成；
   - 没有命令 → `--artifact 证据文件`；标准档也可以 `--evidence "文字"`，记为未验证；
   - 做完但还没法验证 → `--status implemented`；
   - 用 `--hours` 记下投入，超过预计一倍时 `status` 会提醒。

**失败怎么计数**：
- 验证命令失败由脚本自动计数：同一个验证命令上次失败、这次改了代码仍失败，计一次。
- 第一次失败是基线（先写测试看红灯不算），代码没变的重跑不计，执行期间代码被改动的运行不算数，非 git 项目不自动计数。
- 没有验证命令的步骤失败，用 `fail ID --note "现象"` 手动记录。
- 达到上限（默认 2 次）时步骤转为 `needs_replan`，脚本拒绝继续执行它，见最后一节。

**已完成的步骤要重做**：`reopen ID --reason "为什么"`。旧证据移入历史，已有的审查结论作废。不要手改 `state.json`，`status` 会发现。

全部步骤完成后，`status` 显示 `stage: review`。`stale_evidence_steps`（命令证据不对应当前代码）要 `verify --all`；`note_only_done_steps`（只有文字证据）要在审查时向用户说明。

## 出了问题

先归类，拿不准就选最接近的一类：

| 类型 | 信号 | 做法 |
|---|---|---|
| **诊断** | 报错、结果不对 | 列 3 个互相独立的可能原因，按排除成本从低到高逐个验证，每次只改一个变量。 |
| **选择** | 实现路径分叉 | 以后改起来便宜 → 给推荐和一句理由，继续；贵 → 做一个最小实验比较，或回到定方向。 |
| **卡壳** | 不知道该查什么 | 说清已试过什么，列出这类问题通常涉及的关键词、工具和隐含前提，挑最便宜的先试。 |
| **跑偏** | 越做越大，或与目标对不上 | 把当前在做的事和决策卡的目标、非目标逐条比对：有意调整就修订决策卡，无意跑偏就回到计划。 |
| **启动** | 一直拖着 | 把当前步骤继续拆，直到出现一个 15 分钟内能开始的动作，只做那一个。 |

向别人或另一个模型求助前，先整理成这样（很多时候写到第 4 项答案就出来了）：

```
1. 目标：这一步要达到什么（贴完成判据）
2. 期望：我以为会发生什么
3. 实际：实际发生了什么（贴原始输出，不要转述）
4. 已试：试过什么、各自结果
5. 约束：不能改什么、时间预算
```

## 失败到上限、回到计划时

只处理出问题的这一步：拆小、换做法、补前置步骤。改完运行 `replan ID --note "改了什么、为什么"`（脚本会核对这一步确实改过），再重新确认计划。确有理由不改（例如外部服务临时故障），用 `replan ID --note … --waive 理由`，同样要用户确认，且再失败一次就会再次升级。

## 常见坑

- 第一步是"搭框架"这类证伪不了方向的准备工作。
- 验证方法写成"自测通过"：谁测、测什么、看到什么算通过？
- 能写验证命令却只写了文字。
- 为了让验证通过而改命令、放宽判据或删测试：计划确认会失效，必须向用户说明理由。
- 把多个步骤合成一次大改动，出问题时无法定位。
- 用户一句"感觉方向不对"就推倒重来。先问：是哪条假设被什么证据动摇了？
