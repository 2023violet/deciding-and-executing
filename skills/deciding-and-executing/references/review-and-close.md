# 审查、复盘与收尾

全部步骤完成、或用户问"可以上线了吗"时，先审查交付物；之后复盘做法；最后收尾，不留下会误导别人的东西。止损或放弃而停下的项目，跳过审查，直接复盘和收尾。

## 目录
- 交付前审查
- 独立复核
- 复盘与回写
- 收尾：归档、知识同步、删除工作区

## 交付前审查

1. **对照成功标准**：运行 `de.py coverage` 取出逐条的证据清单，再自己确认测试是否真的覆盖了用户要的行为（怎么判断见 [verification-strategy.md](verification-strategy.md)）。缺证据的条目不算通过，哪怕"看起来没问题"。`READY_FOR_INDEPENDENT_REVIEW` 只表示关联的命令通过、文件没变；需要真实设备、浏览器画面或用户验收而没有做到的，写 `NOT_VERIFIED`。
2. **对照非目标**：有没有做了决策卡里说不做的东西？有没有临时方案冒充正式方案？
3. **找问题**：最可能出错在哪？哪条假设还没被验证？用户第一次用最可能卡在哪？
4. **独立复核**：见下一节。
5. **重新验证**：`de.py verify --all`，让命令证据对应当前代码。
6. **记录结论**（照 `next` 走，预览先给用户看，用户同意后才带 `--confirm`）：
   - 可交付 → `review --verdict pass [--independent-report]`。有未完成步骤、过期证据、高风险档只有文字证据、或带阻断项时，脚本拒绝。
   - 修复后可交付 → `review --verdict fix --blocker "必修项" ...`，每个必修项作为新步骤加回计划。
   - 不可交付 → `review --verdict fail --blocker "原因"`，判断是回到计划还是回到定方向。

审查结论绑定当时的代码和计划；之后任一改动，结论自动失效，需要重新审查。

## 独立复核

高风险档必须做，标准档建议做。在同一个对话里审自己的产物，独立性有限（见 [evidence.md](evidence.md)）：发现问题的和确认问题的最好不是同一个上下文。

- **宿主支持子代理时**：派一个没有执行上下文的子代理。只给它决策卡的成功标准与非目标、`plan.json`、固定版本的改动（提交号或 diff 范围）和报告模板 `assets/independent-review.md`；**不给**开发过程、你的推理和你的结论。让它对每条成功标准自己取证，判定 PASS / FAIL / NOT_VERIFIED，写进 `.decision/independent-review.md`。
- **不支持子代理时**：请用户开一个新会话或换一个模型，给同样的材料。
- 告诉复核者：没发现问题是合法结果；每个问题都要附复现方式，复现不出来的不算问题。否则它会为了显得尽职而硬挑毛病。
- 复核结论里的 FAIL 和你没想到的 NOT_VERIFIED 都要处理，不能因为"我验证过了"就忽略。
- 记录结论时加 `--independent-report`，脚本会记下报告的哈希；报告之后被改动或删除，审查结论自动失效。这只防事后篡改，**不能证明复核者真的独立**：独立性靠你只给它上面那些材料。

## 复盘与回写

`.decision/retro.md` 已由 init 创建。归档时脚本会检查"原本预期""实际发生""差异的原因"三节有实质内容。答案以文件为准（决策卡、plan.json、state.json、events.jsonl），不凭回忆：

1. **原本预期什么**：读决策卡和计划。
2. **实际发生什么**：读 `progress.md` 或 `de.py handoff`。
3. **差异的原因**：分开决策质量与结果质量。以当时掌握的信息，这个决定合理吗？当时有没有便宜的办法拿到更多信息？
4. **下次保持什么、改变什么**：每条落成一个具体动作或一条规则。能变成自动检查的，优先变成检查，而不是多写一行规则（模板里的"环境改进"一节）。

回写：
- 决策卡的关键假设表：每条标上 已证实 / 已证伪 / 未验证，并写依据。
- 估算偏差：对比各步 `estimate_h` 与 `spent_h`，有系统性偏差就告诉用户下次乘上这个系数。
- 教训去向：在 retro.md 的表里逐条决定放进规则文件、docs、本技能的 Gotchas，或不记录。没有新教训也是合法结果。

## 收尾：归档、知识同步、删除工作区

三步各管一件事：**归档**只写决策记录、不删任何东西；**知识同步**由 closing-out 审计整个仓库，脚本核对审计没有 error、没被截断、对应当前代码；**删除**要求前两步完成、工作区已提交到 git（删了能恢复），并经用户确认。只做了归档不算结案。`status` 的阶段依次是 `closeout` → `archived` → `ready-to-purge`。

**常规做法（装了 closing-out）**：
1. 按 closing-out 的完整档完成知识同步，把报告存为 `.decision/closeout-report.md`。
2. `de.py closeout --report .decision/closeout-report.md`：预览决策记录写到哪、有什么问题；用户同意后加 `--apply`，一步完成归档并现场重跑审计。审计没通过时，决策记录已写入、状态停在 `archived`，修好后运行 `sync --report …` 即可。
3. 提交所有改动（包括 `.decision/` 和决策记录）。
4. `de.py purge` 返回将删除的文件清单，**给用户看，用户同意后**才 `--confirm`。工作区里有 de.py 不认识的文件时，脚本拒绝删除。删除后提交，再审计一次确认没有残留。

也可以分开做：`archive` → `sync --report …` → `purge`。以"止损"或"放弃"归档时用 `archive --outcome 止损 / 放弃`。

决策记录里每一步的证据都标明类型：命令（附退出码与代码指纹）、文件（附哈希）、文字（标"未验证"）。决策记录写完就不再改，现状写在 README 和 docs。

**没装 closing-out 时**不能运行 `sync`，工作区保留不删，并如实告诉用户"未做脚本化的知识同步"。至少做完：
- [ ] README 的功能、命令、路径与现状一致（实际运行过启动和测试命令）
- [ ] 规则文件（AGENTS.md / CLAUDE.md）没有引用不存在的路径和命令
- [ ] 复盘里每条教训都已放到对应位置
- [ ] 计划草稿、调试脚本、旧副本已列入删除候选

**只是一次会话结束、项目还没完时**：不归档。本次改动影响了 README 或规则文件里的命令、路径、名字，就交给 closing-out 的轻量档，并附上 `de.py handoff` 的输出给下一个会话。

## 常见坑

- 用户问"可以上线了吧"时顺着说"可以"。
- 把 `coverage` 的 `READY_FOR_INDEPENDENT_REVIEW` 当成"已验证完成"。
- 复盘只写"下次注意"，没有落成具体动作；或把失败全部归因于运气，或全部归因于决策。
- 只做了归档就宣布结案；审计之后又改了文档，却拿旧结果去同步。
- 跳过归档直接删工作区：决策理由和被推翻的假设就此丢失。
