# 验证策略：先选证据，再标记完成（R2）

这是 ②计划和 ④审查按需加载的决策表，不增加第六阶段。**验证充分性是专业判断，`de.py coverage` 只检查已记录的覆盖关系和证据时效，不可代替验收。**

| 交付成果 | 最小可观察证据 | 重要的盲区 |
|---|---|---|
| 纯函数/算法 | 单元测试 + 非正常输入/边界条件 | 集成、性能和未测试输入 |
| 多模块功能 | 集成测试 + 回归测试 + 人工审查 diff | 与外部系统交互、上下文外需求 |
| GUI / 网站 | 自动交互 + 实际截图/视觉检查 | 用户可用性、跨设备和浏览器 |
| 硬件/嵌入式 | 模拟验证 + 实物功能与故障注入 | 电磁环境、温度和未测硬件版本 |
| 服务部署 | 自动测试 + 隔离环境演练 + 可观测性 | 生产的配置、容量、网络差异 |
| 研究/架构决策 | 独立事实来源 + 关键假设的最小实验 | 证据偏差、不可迁移的样本 |
| 文档同步 | 静态扫描 + 源码事实比对 + 运行文档命令 | 静态扫描无法理解事实真假 |

## 逐项执行

1. 从 `decision-card.md` 的编号成功标准倒推至少一个*真实可观察*结果；未要求的检测不要机械添加。
2. 每个 `plan.json.steps[]` 用 `covers` 指向所服务的成功标准，明确测试环境与输出来源。
3. `de.py preflight`：先核对工作分支、用户改动、需要执行的 Shell 命令；**任何 Shell 命令都可能有副作用，风险提示不是沙箱**。
4. 执行验证后运行 `de.py coverage`，逐项读步骤状态和 `COMMAND_PASS / ARTIFACT_INTACT / UNVERIFIED_NOTE / STALE / PENDING`。
5. **即使全部 `READY_FOR_INDEPENDENT_REVIEW` 也不意味着通过**。独立审查要从需求开始核查测试覆盖、可信信源和真实产物；无法实际观察的标 `NOT_VERIFIED`。
6. 真正高风险或不可逆动作，必须经过用户许可并使用宿主权限/沙箱。脚本确认 token 不等于人类批准。

## 证据诚实性

- `COMMAND_PASS`：只能证明计划中配置的命令成功且记录的代码指纹未变；不能证明测试本身有效、命令无副作用或需求全面满足。
- `ARTIFACT_INTACT`：只能证明文件仍存在且内容哈希未变；不能证明文件内容真实。
- `UNVERIFIED_NOTE`：用户/Agent 描述属于工作记录，不得标记客观验证。
- 不同设备、不同运行系统、不同 Git 版本的结果不能自动互换。
- 任务失败时先判断是环境问题、实现问题、验收方法问题还是方向假设问题；只回退必要的层级。
