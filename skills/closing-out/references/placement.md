## 判断一条信息该放哪

按顺序问：

1. **下一个 Agent 不知道它，会不会做错事？** 会 → 规则文件。
2. **人要用、要运行、要理解这个系统，需要它吗？** 需要 → README 或 docs/。
3. **它解释的是"为什么当初这样选"？** 是 → 决策记录。
4. **它只是"发生过什么"？** 是 → git 提交说明或 CHANGELOG，不进文档。
5. **它是个人偏好或一次性的小教训？** 是 → Agent 记忆（需用户同意），或者干脆不记。

都不是 → 不记。没有新教训是正常结果。

## 规则文件的写法

规则文件每次会话都会整份加载，每一行都在占用所有人的上下文。

- 只写约束和命令，不写解释性段落。一条规则一行。
- 写清"做什么"，必要时加一句"为什么"，不写"可能""建议考虑"。
- 引用的路径、命令必须存在（审计的 `rule-refs` 会检查）。
- 不写已完成的待办、历史、个人偏好。
- Claude Code 建议每个 CLAUDE.md 少于 200 行；只在某个目录有效的规则，放到那个目录的规则文件或 `.claude/rules/`。

没有规则文件的小项目，收尾时可以新建一个最小版本（少于 60 行），只写五件事：
```
# 项目名
一句话：这是什么。
## 运行
安装、启动、测试命令（各一行，已验证可运行）
## 技术栈
## 目录约定
## 现状与下一步
```

## 一份规则同时服务 Claude Code 与 Codex

- Codex 从仓库根目录往下逐层读 AGENTS.md（同目录有 AGENTS.override.md 时读它），合并后默认最多加载 32 KiB。
- Claude Code 在 CLAUDE.md 不存在时会读 AGENTS.md；两者同时存在时只读 CLAUDE.md，除非 CLAUDE.md 导入了 AGENTS.md。
- 推荐做法：AGENTS.md 是唯一规则源；CLAUDE.md 只写：

```markdown
@AGENTS.md

## Claude Code 专属
（只放 Claude 才需要的内容，例如何时用 plan mode）
```

- 也可以用符号链接 `ln -s AGENTS.md CLAUDE.md`，但在 Windows 克隆里可能变成一行文本，团队里有 Windows 用户时用导入。

## 记忆何时进文档

Agent 记忆（例如 Claude Code 的 `~/.claude/projects/<项目>/memory/`）是机器本地的，换机器、换同事就没了。满足任一条件时，把它"毕业"进文档或规则：

- 它描述的是稳定的机制，不是一次性情况；
- 同一条教训出现了第二次；
- 其他维护者也必须知道。

毕业后，记忆里只留一行指针或删掉（需用户同意）。收尾时默认只读记忆，发现记忆与现状矛盾时，在报告里列出，由用户决定。

## 决策记录的格式

放在 `docs/decisions/YYYY-MM-DD-名称.md`，一个决策一个文件，顶部写状态（已结案 / 已被某决策取代）。内容：背景与问题、结论、关键假设及其最终状态（已证实 / 已证伪 / 未验证）、结果、教训。deciding-and-executing 的 `de.py archive` 会按这个格式生成。

决策记录写完就不再改动其中的事实；决策被推翻时，新建一个决策记录并在旧记录顶部标"已被 xxx 取代"。

## 文档的写法

- 读者打开就能看到当前答案，不需要读完历史才知道现状。
- 就地改写，不追加"更新："段落。
- 一个事实一个权威位置；中英双语文档是例外，但两种语言的命令、数字、路径要同时更新。
- 用绝对日期。
- 能运行的命令要真的运行过；运行不了的标"未验证"。
