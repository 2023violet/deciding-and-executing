## 一、方法

1. **先复现，后认同。** 每条发现先在隔离的临时仓库里对 v3.0.0 复现，复现不了的不改。
2. **先写失败的测试，再修代码。** 每个修复都有一个在 v3 上会失败、在 v4 上通过的回归测试。
3. **测试本身也要被检验。** 对关键约束做变异测试（故意改坏代码，看测试能否发现），发现了一个没有区分度的测试。
4. **测试与环境隔离。** 所有测试与使用者的 git 全局配置隔离。

## 三、评审之外的自审发现

| 发现 | 影响 | 处理 |
|---|---|---|
| 在项目子目录运行 `de.py` 会另建一个 `.decision/` | 同一件事出现两份状态，新会话可能读错 | 统一定位到 git 仓库根 |
| 新名字是旧名字前缀时（`fetchUserData`→`fetchUser`），旧名残留漏报 | 收尾报告误称"已无残留" | 先遮蔽新名字的出现位置，再搜索旧名字 |
| 规则路径检查用 `lstrip("./")`，把 `.github` 变成 `github` | 目前被兜底逻辑掩盖，但随时会误报 | 只去掉开头的 `./` |
| 测试没有与使用者的 git 全局配置隔离 | 开启提交签名时 32 项中 12 项报错；这很可能就是评审方看到"超时"的原因之一 | `helpers.py` 统一设置 `GIT_CONFIG_GLOBAL=/dev/null` 等 |
| 截断测试的夹具同时含有 error，变异测试显示它测不出"截断仍算通过" | 测试通过，但保护不了它声称保护的行为 | 改为只有 warn 的夹具 |

另有一个过程问题如实记录：做变异测试时，shell 超时打断了"注入缺陷 → 运行测试 → 恢复"的循环，被改坏的 `de.py` 留在了磁盘上。逐字节比对发现了这一点，已从备份恢复。此后的变异测试都在恢复后再做一次比对。

## 四、不同意或需要澄清的地方

1. **"引入一次性确认令牌或明确的外部授权机制。"** 令牌已实现，但脚本无法分辨按回车的是人还是 Agent。评审本身也指出"令牌不能代替真实授权"。我把授权拆成三层，并在文档里写清每层能保证什么：脚本（防误操作、防确认过期内容）、流程（必须把 preview 给用户看）、宿主（Claude Code `permissions.ask`、Codex `prompt` 规则）。宿主规则匹配的是命令文本，同样不是安全边界。所以 v4 **不宣称**能阻止一个蓄意违反流程的 Agent，只宣称能阻止"照常调用时绕过人"。
2. **测试超时。** 在干净环境下，v3 的测试用 6.8 秒跑完，不是死锁；但在开启提交签名的 git 配置下有 12 项报错，说明测试确实不隔离。v4 的测试数量增加了约一倍，并且大量启动 git 子进程，完整运行需要几十秒，**12 秒窗口仍然不够**。这是测试规模带来的，不是阻塞；具体耗时见 CHANGELOG。
3. **F-14 实际耗时。** 没有用"开始时间到现在"的日历时间来判断超时：人会中断、会过夜，日历时间会大量误报。改为由执行者用 `--hours` 自报投入。代价是依赖如实填写。
4. **F-16 事务。** 没有实现完整事务与自动恢复，只保证"中断可被发现"。对单人工作区来说，自动恢复的复杂度不值得。
5. **版本号。** 评审建议发 v3.0.1 补丁。由于移除了一个参数、改变了决策卡格式，按语义化版本规则发为 4.0.0；架构确实没有重写，评审肯定的六点全部保留。

## 五、无法由脚本消除的剩余风险

| 风险 | 为什么脚本解决不了 | 缓解 |
|---|---|---|
| Agent 自己取 token 自己确认 | 脚本无法分辨人与 Agent | 流程规则 + 宿主审批规则；行为评测 #7 |
| 宿主规则被换一种命令写法绕过 | 规则匹配命令文本 | 文档明确说明；重要项目不使用 bypass 模式 |
| 文件证据内容不真实 | 脚本只能记录哈希 | 审查阶段人工检查；高风险档优先写 `verify_cmd` |
| `verify_cmd` 本身写得太弱（例如 `true`） | 命令的充分性需要判断 | 闸门 B 的 preview 逐条列出命令，由用户确认 |
| 文档语义与代码不一致 | 静态审计不理解语义 | closing-out 的源码事实核查与报告分层 |
| Agent 行为层未经独立评测 | 需要在真实 Agent 上运行 | `dev/evals` 已备好 15 个用例，待在 Claude Code 中运行 |

另外两项环境限制：只在 Linux 上测试过；非 git 项目无法判断证据是否对应当前代码，也不能删除工作区。
