# v6 方案：减重与去"表演味"

> 2026-11-19。基线：`main` 上的 v5.0.0（deciding-and-executing 5.0.0 / closing-out 2.2.0）。
> 来源：
> - v5 之后的整体评估（结论：工程扎实，但核心收益未验证、使用偏重）；
> - 对一篇高赞 Agent 提示词文章及其评论区的剖析。
>
> 状态：**待审**，未改任何代码。用法：按编号批准。标【行为变更】的会改变用户可见的行为，需要你先拍板。

---

## 〇、结论

**要减的是"负担"，不是"证据"。** v6 只减三样东西：
- Agent 每次要读的文字；
- 用户要填和要确认的东西；
- 说话方式里的"流程表演"。

不动的是两样：
- 证据链（验证命令当场跑、证据绑定代码指纹、失败自动计数、不能验证的必须标出来）；
- 高风险档的全部要求。

**"通用"是指同一个核心场景门槛更低，不是把场景铺得更宽。** 非 git、没有测试的任务，脚本强制不了，不假装能强制。

**先量，再减，减完再量。** 每一项都有数字和回退条件。

## 一、为什么现在做

| 依据 | 说明 |
|---|---|
| 用户对"工程表演"的反感是真实存在的 | 那篇文章评论区点赞最高的两条，都在讽刺 Agent 把小改动做成"哈希、基线、门禁、回滚"的大工程。有人的全局 AGENTS.md 核心一句是 *Do the engineering work, not the engineering theater*。我们的词汇表（指纹、闸门、证据、两步确认）和被讽刺的高度重合。 |
| 现状偏重 | 走一次标准流程，Agent 大约要读 2.8 万字符：SKILL.md 约 1.0 万，五份阶段文档约 1.3 万，验证策略约 0.1 万，第一次使用时还有端到端示例约 0.4 万。SKILL.md 正文里"闸门"出现 13 次，"证据"19 次。 |
| 描述改得更主动后，误用风险会上升 | v5 把描述改成"在回答或动手之前先调用"，正例触发从 8/18 涨到 16/18。同样的写法也可能把技能拉进本不需要它的小任务；现有反例里缺"大词但其实是小任务"这一类。 |
| 外部做法支持"把纠正变成检查" | 评论区转述的 Lauren Tan 演讲主张：每纠正一次 Agent，先问能否变成确定性检查，而不是往文档加一行。这和我们的脚本闸门同向。转述里的具体数字前后不一，未核实，不作证据。 |

## 二、先建立基线（S0，必须先做）

**S0 量出现在有多重**
- 用 2 个真实任务各走一遍：一个跨天的标准档任务，一个本该"不走流程"的小任务，记录下面四个数。
  - **Agent 读入的技能文字**：字符数，按读了哪些文件统计；
  - **用户被要求确认或填写的次数**；
  - **从开始到第一步动手的耗时与轮数**；
  - **小任务是否被误拉进完整流程**。
- 同时给触发评测补 6 条"大词小事"近似反例，例如"帮我想清楚这个变量该叫什么""这个函数先别急着改，给我讲讲"，中英各半，先测基线。
- 产出：`dev/eval-runs/v6-baseline/` 下的记录和触发评测结果。
- 这一步不改技能，只是测量。

## 三、减重措施

### A. Agent 读的东西

**A1 SKILL.md 压到约 80 行**
- 只留：什么时候用；选哪一档；三条硬规则（照 `next` 走；带 `needs_user` 的预览必须先给用户看；不能验证的写明"未验证"）；去哪里看细节。
- 移出去的内容：
  - 命令表 → `de.py --help` 和 `next` 已经覆盖；
  - 证据规则细节 → stage-3；
  - 代码指纹说明 → `references/` 里的一份"脚本说明"；
  - 与 closing-out 的分工 → 一句话加链接。
- 衡量：SKILL.md 字符数，目标降到现在的一半以下。

**A2 五份阶段文档合并成三份，并且按需读**
- `direction.md`：定方向，含按轮提问、钢人论证、事前验尸。
- `plan-and-execute.md`：计划与执行，含失败分诊。
- `review-and-close.md`：审查、复盘与收尾，含独立复核。
- 规则：Agent 只在 `next.why` 指向某份文档，或当前阶段需要时才读。删掉阶段文档里和 `next` 重复的"下一步做什么"段落。
- 衡量：一次标准流程读入的字符数，目标比基线少 40% 以上。

**A3 示例和设计依据移出常规阅读路径**
- `worked-example.md`、`example-decision.md`、`evidence.md` 保留，但 SKILL.md 只在"第一次使用"或"用户问为什么"时才指向它们。现在就是这样，A1 精简后要确保这条规则不丢。

### B. 用户填和确认的东西

**B1【行为变更】标准档决策卡最小化**
- 标准档必填只剩三项：目标、编号的成功标准、止损（期限、触发状态、动作）。
- "非目标""关键假设"改为选填，但填了就进入闸门哈希；高风险档仍全部必填。
- 影响：
  - `card_errors` 按档位区分；
  - 闸门 A 的哈希规则对"未填的选填项"要保持稳定，避免旧工作区闸门失效。要加回归测试。

**B2 帮用户写验证命令**
- 新增：`init` 或 `check plan` 时，检测仓库里已有的测试和检查入口（`package.json` 的 test/lint 脚本、`pytest`、`Makefile` 的 test/check、`just` 配方），在计划模板或 `check plan` 的输出里给出候选 `verify_argv`。
- 只建议，不自动写进计划；采不采用由 Agent 和用户决定，确认仍走 gate B。
- 理由：写验证命令是用户最大的摩擦，也是脚本能不能强制的前提。

**B3 确认次数不增加**：维持标准档 2～3 次，v6 不新增任何确认点。

### C. 去"表演味"

**C1 措辞审查（文档和脚本输出）**
- 范围：两个 SKILL.md、阶段文档、`next.why` 与 `brief`、`handoff` 的文案，中英各一套。
- 规则：用平常话说要做什么、为什么。术语只在第一次出现时解释一次；一个句子里不堆两个以上的术语。用正面写法说清该做什么，少用"禁止""不得"。
- 衡量：用一份小词表统计"闸门、证据链、指纹、两步确认、门禁、基线"等词在 SKILL.md 里的出现次数，目标降到现在的一半以下。删的是重复和堆砌，概念本身保留。

**C2 档位判断放到最前面，拿不准就选轻的**
- SKILL.md 开头第一节就是"这件事有多大"：不走流程 / 轻量 / 标准 / 高风险，各给一句判断标准和一个例子。
- 明确默认值：拿不准时选更轻的一档，执行中发现低估了再升档（现有规则，位置提前、措辞加重）。
- 描述里保留"不用于小修复、单纯问概念"，并用 S0 新增的近似反例监控误触发。

**C3【行为变更】轻量入口 `de.py prove`**
- 用法：`de.py prove -- <验证命令>`，不需要工作区、决策卡和计划，任何 git 仓库、任何任务大小都能用。
- 行为：运行命令；记录退出码和执行前后的代码指纹（执行期间代码变了不算通过）；输出"已验证 / 未通过 / 未验证（非 git）"和一行说明。
- 不落盘：结果只输出，不写工作区。存在工作区时，在输出里提示可以用 `step … --status done` 记入证据。
- 定位：给"这改好了吗、能上线吗"这类最常见的问题一个一句话的入口；完整流程仍只在跨会话、返工代价高时使用。
- 风险：可能被当成完整流程的替代。缓解：输出里写明它只证明"这条命令在当前代码上通过"，不等于需求满足。

### D. 把"纠正"变成检查

**D1 维护规则写进仓库**
- 在开发说明（`README` 的"修改技能的流程"和 `CHANGELOG` 约定）里加一句：每次发现 Agent 用错技能，先考虑能不能变成 `de.py check` 或 `audit.py` 的一条检查，再考虑往文档加一行。
- 本版要下沉的候选：
  - 成功标准是否编号、能否观察（已有）；
  - 计划步骤有没有"完成判据"（已有）；
  - 新增：验证命令写在 `verify_cmd` 里却用了 POSIX 专用语法（Windows 上会失败）时，在 `check plan` 中给警告。

**D2 独立复核不编造问题**
- `assets/independent-review.md`（中英文）和 review-and-close 文档加一条：没发现问题是合法结果；每个 FAIL 都要附复现证据，没有证据的不算问题。
- 改动很小，可以直接做。

### E. 最便宜的通用入口

**E1 重写 `prompts-standalone.md`**
- 给没装技能、或在不能运行脚本的环境里的人用：每个阶段一两句可以直接复制的话。例如：
  - "先别急着给答案：问我几个会改变结论的问题，每题附你的推荐答案。"
  - "假设你现在的方案是错的，找能推翻它的证据。"
  - "说'完成'之前，先运行能证明它的命令，把输出给我看。"
- 文件开头说明：这一版没有脚本保证，只是提示词。

## 四、明确不做

1. 不拆成多个单点技能。
2. 不为了显得轻而把任何脚本闸门降级成提示词；高风险档要求不变。
3. 不扩展到非 git、没有测试的场景并假装还能强制。
4. 不新增方法论名词，不把文章里的提示词整套塞进技能。
5. 不追求脚本行数下降：脚本不被模型阅读，行数只影响维护，不影响使用成本。

## 五、衡量与回退

| 指标 | 基线（S0 测） | 目标 | 回退条件 |
|---|---|---|---|
| 标准流程中 Agent 读入的技能字符数 | 约 2.8 万（估算） | 下降 ≥ 40% | — |
| SKILL.md 字符数 | 约 1.0 万 | ≤ 0.5 万 | — |
| SKILL.md 术语词表出现次数 | S0 统计 | 下降 ≥ 50% | — |
| 小任务被拉进完整流程 | S0 测 | 0 | 任何一次就回查 C2 |
| 触发评测：正例 | 16/18、13/13 | 不下降超过 1 条 | 下降 ≥ 2 条则回退对应描述改动 |
| 触发评测：反例（含新增近似反例） | 32/32 + 新增 | 全部正确 | 出现误触发则回退 |
| 用户确认 / 填写次数（标准档） | S0 测 | 不增加；B1 后填写项减少 | — |
| 回归测试 | 174 项通过 | 全部通过 | 失败不合并 |
| 证据规则 | 现状 | **不变**：有验证命令的步骤仍须当场通过；文字证据仍标未验证 | 任何放松都不合并 |

**底线**：如果某项减重让"假完成"更容易发生，比如能不跑验证就标完成，这项不合并，无论省了多少字。

## 六、顺序

1. **S0** 测基线。
2. **改动小、可直接做的**：D2（复核不编造）、C2（档位前置）、E1（重写独立提示词）。
3. **减 Agent 阅读量**：A1、A2、A3，同时做 C1 的措辞审查。
4. **【行为变更】**：B1（最小决策卡）、C3（`prove`），先给你看细化后的设计，批准后再做。
5. **B2**（验证命令候选）、**D1**（新增 `check plan` 警告）。
6. **复测**：重跑 S0 的四个数字和触发评测，写进 CHANGELOG。版本号定为 deciding-and-executing 6.0.0（B1 改变决策卡要求，算不兼容变更）和 closing-out 2.3.0。

## 七、需要你拍板

1. **B1**：标准档决策卡是否只保留三项必填（目标、成功标准、止损）？
2. **C3**：是否新增 `de.py prove` 轻量入口？
3. **S0**：基线用哪两个真实任务？我建议一个你接下来真要做的跨天任务，加一个日常小改动。
4. **评测额度**：v6 结束时的复测约 200 次 `claude -p` 调用，按上次的经验大概要分两段跑。可以接受吗？
