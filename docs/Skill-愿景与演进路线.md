# Deciding & Executing｜产品愿景与演进路线

> 2026-10-13 · 本文是下一代架构设计建议，不代表 v4.0.1 已经实现下文列出的全部能力。

## 1. 一句话愿景

**让 AI 从“给出看似正确的建议”，进化为“围绕真实目标运行可追溯、可证伪、可中断且可恢复的工作”。**

定位：**轻量的 Agent 任务生命周期治理层**，而不是“万能思考 Prompt”、另一个通用编排框架或代替人的自主项目经理。

### 明确不做什么

- 不替代编码、查阅资料、调试、GUI 观感评审、实际硬件测试等领域技能。
- 不把所有 Prompt 笔记中的思维方法常驻上下文；按问题诊断再加载。
- 不把作者自评、计划完成、`exit 0` 或静态审计 0 error 宣传为“工程事实已完全验证”。
- 不自称能在脚本内部辨别人类授权；高风险动作必须依赖宿主实际权限系统与外部确认。
- 不要求一个十分钟的可逆任务走完整套决策卡与归档流程。

## 2. 思想基因 → 工程能力

| 原始方法 | 形成的系统行为 | 外部证据/限制 |
|---|---|---|
| 未知的未知、苏格拉底提问 | 必要时澄清目标、识别关键遗漏 | 仍由语言模型判断，不是脚本证明 |
| 双向钢人、第一性原理 | 有争议时检验候选方向及反方论证 | 结构化反方不构成独立信源 |
| 反向思考 / Pre-mortem | 可预见失败、应变预案、止损信号 | 风险列表可能不完整 |
| 最小实验 | 把最危险假设放到前期验证 | 真实实验需有有效测量，不保证外推正确 |
| 延迟判断 | Gate A/B 绑定决策和计划 | token 并非真人授权 |
| 目标约束与上下文工程 | 决策卡、plan、progress 的外部记忆 | 过时状态也会污染后续会话 |
| 执行期分诊、局部升级 | 一步一验、失败进入 replanning | 自动升级无法判定根本原因 |
| 事实核查、对抗性审查 | 记录执行命令/文件证据、审查失效 | 有通过证据不代表需求完备 |
| 复盘与知识回写 | closing-out 同步与历史记录 | 静态审计无法理解语义 |

## 3. 目标用户及高价值情境

目标是同时使用 Claude Code、Codex 或相似编码代理，且跨会话、跨人员推进工程项目的个人/小团队。

1. **模糊目标/不可确定选型**：先问“为什么做”，找出可证伪假设，再计划。
2. **已有明确任务合同**：跳过重型论证，先对齐合同与测试，然后小步实施。
3. **执行中失败**：从“盲试第三次”转为局部诊断和升级。
4. **长程会话/交接**：状态不依赖一段聊天记忆，允许新 Agent 从真实仓库恢复。
5. **里程碑关闭**：事实与文档同步，历史与现状分层存放。

明确不适合：随手的事实问答、简单措辞修改、一次性低风险命令、未经独立验证的不可逆生产变更。

## 4. 最终版应该长什么样

### 外部体验：一个入口，按需选择流程

```
用户目标 / 现有任务合同
       ↓
Intake：识别任务类型、风险、可逆性、证据可得性
       ├─ Quick：明确可逆任务 → 直接做 + 验证，零持久化
       ├─ Standard：方向清楚 → 合同对齐 + 小步计划 + 验证
       └─ Discovery / High-risk：关键不确定性 → 研究/最小实验 + 人工决策
       ↓
Execution Loop：下一步 → 运行 → 记录证据 → 查偏差/升级
       ↓
Review：独立抽查 + 证据与验收一一映射
       ↓
Closeout：知识同步 + 后续可恢复的简要交接
```

### 内部结构：双 Skill 保留、扩展按需调用

- `deciding-and-executing`：**控制平面**，负责入口分流、计划状态、闸门、证据登记、失败升级与审查。
- `closing-out`：**知识与状态维护平面**，负责影响面梳理、审计、规则更新和历史归档。
- 可选能力包（暂不实现）：`decision-research`（事实查证/横纵比较/异质信源）、`experiment-design`（最小实验方法）、`independent-review`（对抗审查）。仅在各自有充分真实用例和比较评测时拆出，不按名词增设技能。

不建议在 v4.0.1 内引入服务端数据库、消息队列、LLM 调度器、多模型辩论管线。对于小团队，本地 `.decision/` + Git 已是更可理解、可撤销的起点。

## 5. 关键的设计原则

**证据优于叙述**：声明、脚本检查、人工验证和真实实验属于不同强度的证据，不能混成一个 PASS。

**审批是边界不是礼仪**：关键内容变化自动使旧审批失效；脚本能阻断错误流程，真人授权仍由外部宿主机制承担。

**失败分级而非全盘推翻**：局部失败回计划，关键假设被证伪才回方向。

**最小认知成本**：优先减少用户必须读的提示词和必须填写的表格。只有可量化地提升执行可靠性的新字段，才应进入核心 schema。

**渐进式披露**：路由 description 仅说明触发条件；SKILL.md 提供路径图与硬边界；详细 SOP、gotchas、范例、脚本按需加载。

**反馈循环而非模板崇拜**：把真实 Agent 行为失误转为回归场景、验证脚本或 gotcha；拒绝“测试数量多就代表质量高”。

## 6. 路线图（独立于本次补丁）

### R0｜v4.0.1：把现有承诺兑现

六项阻断修复、回归测试与发布包校验。不得新增业务能力。当前交付就是这一阶段的候选实现。

### R1｜真实使用的对照评测（首要）

拿 12–20 个小而真实的工程任务，随机或配对比较：原生 Agent、只提供任务合同、安装本 Skill。记录四个指标：**成功率、误完成率、人工干预次数、成本/完成时间**。另设 15 个“应触发/不应触发”用例测触发精确率与召回率。提前固定评分规则，不能由执行 Agent 给自己评分。

最重要的决策门槛：只有在质量收益足以抵消使用成本时，才允许扩大默认使用范围。

### R2｜证据合同 v2

逐项把成功标准映射到证据类型、版本与运行环境；显式记录 `unverified / pass / fail / stale`。对依赖被 Git 忽略文件或外部硬件的测试，允许声明非源码输入摘要。保留降级使用，不把所有任务强行拉到高风险模式。

### R3｜可解释的自动分流与状态恢复

提高“任务太简单就跳过”与“中断后恢复”能力；把下一步需要的事实压缩到可审计摘要，降低长上下文依赖。只在 R1 真实评测证明有用后考虑。

### R4｜高风险宿主权限和跨平台验证

在 Windows、macOS、Linux，以及 Claude Code 与 Codex 上做真实只读/模拟审批测试。验证宿主权限规则的匹配行为，不在用户生产项目做破坏性实验。

### R5｜生态扩展（有需求才做）

通过明确定义的接口调用研究、实验、设计、代码审查等专业 Skill。多 Agent 分工不是目标；**真正独立的数据、测试和核验能力**才值得引入。

## 7. 什么时候算最终版

不是“所有概念都写全”，而是同时满足：

1. **行为**：真实任务中误完成、盲试、无授权写入和交接丢失显著减少。
2. **成本**：简单任务不会被不必要的流程拖慢；用户只看到当前需要批准的关键内容。
3. **证明**：独立对照评测、跨平台回归和完整发布链均有可检查的证据。
4. **可靠**：已知 P0/P1 被关闭；安全策略以实际宿主规则验证，而非文案替代。
5. **可维护**：双 Skill 之间的契约小而稳定，失败分层清楚，版本迁移可解释。

> 产品最值得追求的竞争力并非“比别人更会写 Prompt”，而是让错误更早暴露、改动可追溯、任务可恢复，并让用户保留真正的决策控制权。

## 8. 参考与证据边界

- OpenAI 官方《Skills》：`SKILL.md` + references/scripts/assets、渐进加载、明确“做什么/何时用”的 description。https://developers.openai.com/api/docs/guides/tools-skills
- OpenAI《Testing Agent Skills Systematically with Evals》：触发、过程、产物的独立评测，而非作者自评。https://developers.openai.com/blog/eval-skills
- OpenAI《Rethinking skills and prompts for GPT-6 Astra》：随着模型增强，重新审视累积的复杂指导和上下文膨胀。https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra
- 来源于用户两份 Prompt 笔记的钢人、最小实验、未知的未知、知识回写等设计，属于方法论输入；它们的组合效果仍缺独立实证，不能当成已验证的事实。
