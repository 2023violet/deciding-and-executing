## 1. 一句话结论

**Skill = 一份可执行的 SOP + 它需要的工具 + 它踩过的坑 + 验证它的测试。** 你们"Skill 是封装完整的 SOP"的理解方向是对的，但只对了一半：纯文字的 SOP 模型会"读了但不照做"，顶尖团队的做法是把 SOP 里的关键检查写成脚本、把踩坑经验写成 Gotchas、再用评测证明它比不装技能时更好。

## 2. Skill 是什么：比"SOP"多三样东西

技能是一个文件夹，里面至少有一个 `SKILL.md`，可选 `scripts/`（可执行代码）、`references/`（按需读取的文档）、`assets/`（模板、图片等产出用素材）。这是 Anthropic 发起、OpenAI 也采用的开放格式，同一个技能文件夹可以在 Claude 和 Codex/ChatGPT 里用。

它和其他东西的分工：

| 东西 | 解决什么 | 什么时候选它 |
|---|---|---|
| 提示词 | 一次对话里的指令 | 一次性任务 |
| 项目说明 / CLAUDE.md / AGENTS.md | 每次都要知道的背景 | 始终适用的约定，内容短 |
| **Skill** | 某类任务的可复用流程与知识，**按需加载** | 反复出现、步骤多、需要特定知识或工具的任务 |
| MCP 连接器 | 让模型能"够得着"外部系统 | 需要读写某个应用的数据 |
| 子代理 | 独立上下文里跑一个子任务 | 需要隔离或并行 |
| Hook | 在某个时机强制执行某件事 | 必须 100% 发生、不能靠模型自觉的规则 |

比 SOP 多出来的三样：
1. **工具**：脚本、模板，让关键步骤不依赖模型临场发挥。
2. **踩坑清单**：Claude Code 团队说这是技能里信号最强的部分，而且是从真实失败里长出来的。
3. **测试**：评测集 + 触发测试，证明它有用、会被用到。

## 3. 三层加载：决定了一切写法

| 层级 | 何时进入上下文 | 预算 |
|---|---|---|
| 1. 元数据（name + description） | 每次会话开始，**所有技能**都加载 | 约 100 token/个；Codex 给全部技能列表的预算约为上下文的 2%（未知时 8000 字符）；Claude Code 列表里单个描述超过 1536 字符会被截断 |
| 2. SKILL.md 正文 | 模型判断相关后才读 | 建议少于 500 行、5000 token |
| 3. references / scripts / assets | 正文指向、且任务需要时才读；脚本只有输出进入上下文 | 基本不限 |

由此推出三条写法：
- **description 是唯一一定会被看到的部分**，必须让模型一眼判断"现在该不该读我"。
- **正文写"每次都要用的"**，偶尔用的放进 references，并写明**什么时候读**（"进入②时读 stage-2-plan.md"比"详见 references/"有用得多）。
- **引用只走一层**：SKILL.md → 参考文件，不要参考文件再链到别的参考文件，模型可能只读一部分。超过 100 行的参考文件加目录。

## 4. 格式规范：Claude 与 Codex 的异同

**开放规范（两边通用）**

| 字段 | 必填 | 约束 |
|---|---|---|
| `name` | 是 | 1-64 字符；小写字母、数字、连字符；不以连字符开头结尾；无连续连字符；与目录同名 |
| `description` | 是 | 1-1024 字符；写清做什么和何时用 |
| `license` / `compatibility` / `metadata` / `allowed-tools` | 否 | `compatibility` ≤ 500 字符；`allowed-tools` 为实验性 |

**Claude 侧额外约束与能力**
- 上传到 claude.ai 或经 API 使用时，frontmatter 只允许上表六个字段，多了会直接报错。
- name 不能含 `claude`、`anthropic`；description 不能含尖括号。
- Claude Code 额外支持：`disable-model-invocation`（只允许手动 `/调用`，适合部署这类有副作用的流程）、`user-invocable`、`context: fork`（在子代理里跑）、`hooks`（技能激活期间生效的钩子）、`paths`、`${CLAUDE_SKILL_DIR}` 路径变量、`` !`命令` `` 动态注入上下文。这些字段在 claude.ai 上传时不被允许，所以跨平台技能要克制使用。

**OpenAI 侧额外约束与能力**
- 可选 `agents/openai.yaml`：`interface`（显示名、25-64 字符的短描述、图标、默认提示词——必须写成 `$技能名`）、`policy.allow_implicit_invocation`（设为 false 则只能显式调用）、`dependencies.tools`（声明依赖的 MCP 服务）。这个文件给宿主界面读，模型本身不读。
- 放置位置：仓库 `.agents/skills`、用户 `~/.agents/skills`、管理员 `/etc/codex/skills`、系统内置。
- 官方建议默认"只写说明"，只有需要确定性行为或外部工具时才加脚本；每个技能只做一件事。

**本次做法**：frontmatter 只用通用字段（保证 claude.ai 能上传），另加 `agents/openai.yaml` 让 Codex/ChatGPT 显示得体。

## 5. description：决定技能会不会被用到

**模型怎么决定用不用**：它只看名字和描述。而且只有在任务超出它"自己就能搞定"的范围时才会去查技能——"读一下这个 PDF"这种一步能完成的请求，描述写得再准也可能不触发。所以测试触发要用有一定复杂度的真实请求。

**两个流派，以及我们的取舍**
- Anthropic 官方公式：**做什么 + 何时用 + 关键能力**，第三人称，带上用户会说的触发词；并提醒模型当前普遍"触发不足"，描述可以写得"积极一点"，例如加上"即使用户没有明说 X 也应使用"。
- 社区（superpowers 技能库）的实测发现：**描述里如果概括了流程，模型会照着描述做而跳过正文**。他们的描述只写"何时用"。
- 两者不矛盾。我们的写法是：**只写触发场景、用户原话式的关键词、边界（不用于什么），不写流程步骤**。

**写法要点**
- 把最主要的使用场景放在最前面（列表截断从尾部开始）。
- 用用户会说的话，而不是你的术语：用户说"接下来怎么做"，不说"交接阶段"。
- 写出边界："不用于一次性事实问答……"可以显著减少误触发。
- 控制长度：本技能 203 个字符，远低于上限，给其他技能留出预算。

**怎么测**：准备约 20 条真实口吻的查询，8-10 条应触发、8-10 条不应触发。不应触发的要选"差一点"的（共享关键词但其实是别的需求，比如"钢人论证和稻草人有什么区别"），而不是"今天天气"这种一看就无关的。每条跑 3 次算触发率，按 6:4 分训练集和验证集，只用训练集的失败来改描述，用验证集选最终版本，避免过拟合。见本仓库 `dev/evals/<技能名>/trigger_evals.json` 与 `dev/run_trigger_eval.sh`。

## 6. 正文怎么写：十条写作规则

1. **只写模型不知道的**。逐段问："删掉这段，模型会做错吗？"不会就删。别解释什么是 PDF、什么是钢人论证。
2. **自由度匹配脆弱度**。多种做法都行的地方给方向（高自由度）；容易出错、必须按顺序的地方给精确命令（低自由度）。像过独木桥要护栏，过草地只要指方向。
3. **给默认值，不给菜单**。"用 A；扫描件改用 B"胜过"可以用 A、B、C、D"。
4. **教方法，不教答案**。写"怎么处理这一类问题"，而不是"这一个问题的答案"。
5. **Gotchas 放正文**。环境特有的、违反常识的事实，是最高价值的内容。每纠正模型一次，就往里加一条。
6. **输出用模板**。模型对具体结构的模仿比对文字描述的理解可靠。
7. **多步骤用清单**。让模型把清单复制到回复里逐项打勾，防止跳步。
8. **校验循环**：做 → 校验 → 修 → 再校验，校验通过才进入下一步。
9. **计划-校验-执行**：批量或破坏性操作，先生成结构化计划文件，用脚本对照事实来源校验，再执行。
10. **讲清为什么，少用全大写的"必须"**。模型理解了目的，就能在没写到的情况下做出正确判断；满篇 MUST 是黄色警告。

还有一条贯穿全部的：**宁可适度详细，不要面面俱到**。覆盖所有边角情况的技能反而让模型抓不住重点、去执行不相关的指令。

## 7. 脚本：把"必须做到"交给代码

为什么要脚本：代码是确定性的。"没有证据不准标记完成"写在正文里，模型大多数时候会遵守；写进脚本，就是每一次都遵守。

给 AI 用的脚本和给人用的不一样：
- **不能有交互式提问**，模型无法回答终端里的提示，会卡死。所有输入走参数。
- **`--help` 就是文档**：写清用途、参数、示例，正文里只需说"运行 xx"。
- **报错要可操作**：说清哪里错、期望什么、下一步怎么做。"无效输入"会浪费模型一个回合。
- **结构化输出**：数据（JSON）走 stdout，提示信息走 stderr。
- **有意义的退出码**，并写在 `--help` 里。
- **幂等**：模型可能重试，"不存在才创建"比"重复就报错"安全。
- **控制输出长度**：宿主会截断过长输出。
- **依赖写清楚**：本仓库的两个脚本都只用 Python 标准库，免安装。

另外，开发过程中如果发现每次测试模型都在重写同一段辅助代码，就是信号——把它写成脚本放进 `scripts/`。

## 8. 把一份 SOP 翻译成 Skill

| SOP 要素 | Skill 里放在哪 | 本技能的做法 |
|---|---|---|
| 目的、适用范围 | description（何时用）+ 正文第 1 节 | 分流规则：可逆、简单的事不走流程 |
| 角色与职责 | 正文表格 | AI 查事实、给推荐、做记录；用户做决定、做验收 |
| 流程总览 | 正文的阶段表 + 简图 | 四阶段，每阶段写明进入条件、退出闸门、产出 |
| 详细步骤 | references/ 每阶段一个文件 | 每个文件 = 清单 + 步骤 + 闸门 + 本阶段的坑 |
| 质量控制点（闸门） | **脚本** + 人工清单兜底 | `de.py check` / `step` / `fail` |
| 异常处理与升级 | 正文专节 | 一级回计划、二级回方向，只改被击中的部分 |
| 表单与记录 | assets/ 模板 + 工作区文件 | 决策卡、plan.json、进度日志 |
| 经验教训 | Gotchas | 十条最常见失误 |
| 培训示例 | references/ 示例文件 | 一个从头到尾的完整案例 |
| 修订记录 | metadata.version + 决策卡修订表 | — |

两个容易漏的点：
- **状态外置**。模型跨会话没有记忆。Anthropic 做长时间任务代理时，靠的是"功能清单文件 + 进度文件 + git 历史"，让新会话一开始就能知道做到哪了。本技能的 `.decision/` 目录就是这个作用，`status` 命令就是"开工先看一眼"。
- **人工兜底**。不是每个环境都能跑代码（例如纯聊天）。每个脚本闸门都配一份人工清单，保证降级可用。

## 9. 评测：没测过的技能等于没写

**先测再写**。Anthropic 建议：先让模型在不装技能的情况下做几个代表性任务，记下它在哪里失败，再针对这些失败写最少的说明。这样写出来的是解决真问题的技能，而不是想象中的问题。

**输出质量评测**（`dev/evals/<技能名>/evals.json`）
- 每个用例 = 真实口吻的提示 + 期望结果描述 +（跑完第一轮后再加的）断言。
- 每个用例**跑两遍**：装技能、不装技能（改进旧技能时用旧版本当基线）。每次都从干净上下文开始。
- 好的断言：可客观检查、可计数、描述清楚（"只问了 1 个问题"）。坏的断言：太模糊（"回答得好"）或太死板（"必须出现某句原话"）。
- 判分要有证据：引用输出原文；有标题但内容空洞，算不通过。
- 看差值：通过率提升多少、多花多少时间和 token。两边都通过的断言没有区分度，删掉；两边都失败的，先怀疑断言本身。
- **人工看一遍输出**，断言只能检查你想到的东西。

**触发评测**：见第 5 节。

**迭代**：把失败的断言、人工反馈、执行记录（不只是最终输出）一起交给模型改技能，要求它：从反馈中归纳一般规律而不是打补丁、保持精简、解释原因、把重复劳动做成脚本。直到反馈为空或不再有明显提升。

Claude 官方的 `skill-creator` 技能把这一整套自动化了（并行跑有/无技能、判分、汇总、生成网页供人工查看、优化描述）。OpenAI 的 `$skill-creator` 负责从零生成技能骨架和校验。

**本仓库的评测状态**见 [CHANGELOG.md](../CHANGELOG.md) 每个版本的"验证"一节（只在那里记录，避免多处数字不一致）。一个值得记下的实例：closing-out 第一次按技能跑示例仓库，就暴露了审计脚本 3 个缺陷——这正是"先跑真实任务再定稿"的意义。

## 10. 分发、度量与维护

- **个人**：claude.ai 上传 zip（设置 → 技能）；Claude Code 放 `~/.claude/skills/`；Codex 放 `~/.agents/skills/`。
- **团队**：Claude Code 放仓库 `.claude/skills/` 一起提交；规模大了做成插件放进插件市场，让人按需安装——每个提交进仓库的技能都会占用所有人的上下文预算。Claude 的组织管理员可以统一下发技能。
- **度量**：Anthropic 内部用一个工具调用前的 hook 记录技能使用情况，用来发现哪些技能"该触发却没触发"。
- **维护**：好技能大多从几行字和一条 Gotcha 开始，随着模型遇到的新坑慢慢长大。版本号写在 `metadata.version`。
- **安全**：只装可信来源的技能；装别人的技能前，读一遍脚本和依赖，留意要求访问外部网络的指令。

**Anthropic 内部技能的九种类型**（好技能通常只属于其中一类）：库与 API 参考、产品验证、数据获取与分析、业务流程与团队自动化、代码脚手架与模板、代码质量与审查、CI/CD 与部署、故障处理手册、基础设施运维。他们说其中"产品验证"类对输出质量的提升最可测量。本技能属于"业务流程"类，并借用了"验证"类的思路（没有证据不算完成）。

## 11. 案例：从 v1 到 v4 改了什么

### v1 → v2

| v1 的问题 | 违反了哪条 | v2 的改法 |
|---|---|---|
| description 写了"先判断阶段……用三个文件衔接"等流程摘要 | 第 5 节：描述概括流程会让模型走捷径 | 只写触发场景和边界 |
| 闸门全靠"不要""必须"的文字 | 第 7 节：关键检查交给代码 | `de.py` 校验决策卡与计划、无证据拒绝标记完成、失败到阈值提示升级 |
| 没有 Gotchas | 第 6 节第 5 条 | 正文第 6 节十条 |
| 没有完整示例 | 第 6 节：模板与示例比描述可靠 | `worked-example.md`，含一级和二级升级各一次 |
| 一种升级：出问题就回到定方向 | 设计缺陷：技术故障不该动方向 | 分为一级（回计划）和二级（回方向） |
| 评测文件放在技能目录里 | OpenAI 建议技能目录不放开发与测试文档 | 运行时文件在 `deciding-and-executing/`，开发文件在 `dev/` |
| 没有 Codex 适配 | 第 4 节 | 新增 `agents/openai.yaml` |
| 没有结构校验 | 第 12 节 | `dev/validate_skill.py` |

### v2 → v3

| v2 的问题 | 违反了哪条 | v3 的改法 |
|---|---|---|
| 流程在"复盘"处结束，项目里的 README、规则文件、残留文件没人管 | SOP 不完整：交付后的知识维护没有归属 | 新增独立技能 `closing-out`（收尾与知识同步）；deciding-and-executing 增加⑤收尾归档 |
| `.decision/` 永远留在仓库，下一个 Agent 会把旧决策卡当现行目标 | 过程文件冒充现状文件 | `de.py archive`：先预览、确认后写入 `docs/decisions/`，再经确认删除工作区 |
| 同一个数字（测试数量）写在 README 中英文和教程三处 | 每个事实只该有一个权威位置 | 数字只写在 CHANGELOG 的"验证"一节，其他地方链接过去 |
| CLAUDE.md 与 AGENTS.md 的关系没人检查 | 平台事实：两者并存时 Claude Code 只读 CLAUDE.md | 审计脚本 `rules-chain` 检查，推荐 `@AGENTS.md` 导入 |

**为什么收尾做成独立技能而不是第五个阶段的全部内容**：触发时机不同（"这件事结束"与"今天先到这"），作用范围不同（一件事 vs 整个仓库），而且很多时候写完代码根本没走决策流程，也需要收尾。官方建议一个技能是一个连贯的工作单元；两个技能之间用一条清晰的接口（`.decision/` 的归档状态）配合，比一个大技能更好触发、更好评测。

### v3 → v4：一次外部工程评审教会我们的事

v3 拿到的评审结论是 REWORK REQUIRED，核心一句话：**规范层提出了严格要求，程序层没有兑现**。Agent 得到"检查通过""归档成功"的结果，就以为关键条件被验证了。复现时发现最严重的一条比评审说的还严重：一条删除命令可以把整个项目连同 `.git` 删掉。

学到的五件事：

1. **规范和脚本必须一致，不一致时以脚本为准来写规范。** SKILL.md 写"必须经用户确认"，脚本却只要一个参数就删除，这比没有规范更危险，因为它给人安全的错觉。做法：列出 SKILL.md 里每一个"必须""不能"，逐条问"脚本会拦住吗"。拦不住的，要么改脚本，要么在文档里明说"这一条靠流程，不靠脚本"。
2. **脚本只宣称它能验证的东西。** 脚本分不清人和 Agent，所以确认 token 只能防误操作，不能当作授权；真正的人工授权要交给宿主（Claude Code `permissions.ask`、Codex `prompt` 规则），而宿主规则匹配命令文本，也不是安全边界。三层各自能保证什么，都要写出来。
3. **证据要能复核，并且绑定版本。** "有一段文字"不是证据；能让脚本当场重跑的命令才是。命令结果还要绑定代码指纹，代码一变就过期，否则旧版本的测试会被当成新版本的证明。
4. **测试要被检验。** 变异测试——故意把关键约束改坏，看测试会不会失败——在本次发现了一个"永远通过"的测试。测试还要与使用者环境隔离：一个开启了提交签名的 git 全局配置，就能让三分之一的测试报错。
5. **发布前用脚本一次性检查所有东西。** `release_check.py` 在本次第一次运行就拦下了两个问题：README 里写错的测试命令，和一个指向尚未写好的文件的链接。

| v3 的问题 | v4 的改法 |
|---|---|
| 删除只靠文字要求确认 | 删除独立成 `purge`：七项前提 + 两步确认 + 推荐宿主审批 |
| 任意文本即可标记完成 | 命令证据由脚本执行并绑定代码指纹；高风险档拒绝文字 |
| 失败升级只是返回一个字段 | `needs_replan` 状态，脚本拒绝继续 |
| 阶段按文件推断 | 阶段由闸门记录决定，闸门绑定内容哈希 |
| 没有风险分级 | 不走流程 / 轻量 / 标准 / 高风险 |

逐条回应见 [内审报告-v4.0.0.md](内审报告-v4.0.0.md)。

## 12. 发布前检查清单

**结构**
- [ ] `name` 合规且与目录同名
- [ ] `description` 写了何时用、用户原话式关键词、不用于什么；没有流程摘要；≤ 1024 字符
- [ ] frontmatter 只含通用字段（要上传 claude.ai 时）
- [ ] SKILL.md < 500 行；参考文件一层深，长文件有目录
- [ ] 每个参考文件都写明"什么时候读"

**内容**
- [ ] 删掉了模型本来就知道的解释
- [ ] 有 Gotchas
- [ ] 有输出模板和至少一个完整示例
- [ ] 多步骤有清单，关键步骤有校验循环
- [ ] 给默认做法，不给选项菜单

**脚本**
- [ ] 无交互；有 `--help`；报错可操作；JSON 输出；有退出码；幂等
- [ ] SKILL.md 里每一个"必须/不能"，都标明是脚本强制还是只靠流程
- [ ] 破坏性操作：路径边界、可恢复性、两步确认、拒绝未知内容
- [ ] 有回归测试，测试与使用者环境隔离
- [ ] 做过变异测试：关键约束被改坏时测试会失败
- [ ] 有一个一次跑完全部检查的发布脚本

**评测**
- [ ] 至少 3 个真实口吻的用例，含边界情况
- [ ] 跑过有/无技能对比，差值值得
- [ ] 约 20 条触发查询（含"差一点"的反例），分训练/验证集
- [ ] 人工看过输出
